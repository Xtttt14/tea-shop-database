# 第一阶段报告：数据库初建与CRUD

## 1. 任务依据与成果

依据用户提供的《第一周任务讲解.docx》中第1—4周安排，完成业务分析、关系模式、建库装载、CRUD、连接查询、统计视图、完整性约束与角色授权。场景按用户要求纳入外卖配送、线上商城、优惠券和储值，不沿用早期候选方案中排除这些服务的设定。

交付15张业务表、6个视图、4个数据库业务角色及4个无登录演示用户；普通顾客、会员和骑手不直接登录数据库。没有提前制作后续阶段要求的网页、存储过程或预测系统。

## 2. 设计思路

商品与原料分离，通过配方表达销售一杯饮品消耗哪些原料。订单明细保存成交快照；订单保存金额组成并以计算列得出应付额。会员余额和积分保留变动流水，汇总查询可核对其结果。配送保存下单时收件快照。券活动和会员持有的券分离，联合外码检查归属，过滤唯一索引限制同时使用。

保留余额、积分和库存汇总，是为了直接回答“还能用多少”；同时保留流水是为了回答“为什么是这个数”。二者的一致性需要事务和对账，不能仅靠字段非负约束保证。

## 3. 实验步骤

1. `00-create.sql`创建独立课程数据库，`01-schema.sql`创建结构和PK/FK/UK。
2. `constraint.sql`增加检查约束，`02-seed.sql`装载虚构但有业务意义的样例。
3. `view.sql`建立菜单、可用库存、制作队列、日销售、商品销量和订单摘要视图。
4. `role.sql`建立角色与无登录测试用户，授予最小演示权限。
5. `crud.sql`演示商品增查改删、库存入库及普通订单完整流程；写入后回滚，不污染基础样例。
6. `services.sql`演示充值50→使用满20减3券→2杯饮品配送应付24→余额付款→耗料→配送送达→积分21→整单退款→余额及积分冲正，全程验证后回滚。
7. `query.sql`执行订单明细连接、配送连接、可用券、销售统计和流水对账。
8. `test.sql`执行金额及数量断言、15项非法数据测试、授权与越权测试。失败使用THROW，让sqlcmd的退出码反映失败。

## 4. 验证结果与证据

实际环境：本机SQL Server 2025 Express（17.0.1000.7），Windows，sqlcmd和ODBC Driver 18；数据库TeaShopCourse。最终执行记录见`evidence/sql-validation.txt`及`evidence/README.md`，以命令退出码和断言结果为依据。

预期：4单5杯，实收70；会员甲余额88、积分33，会员乙余额0、积分18；库存、余额和积分对账差异为0。15项非法写入均应被拒绝，包括负库存、超额预留、负余额、孤立明细、重复编号、非法券有效期、使用他人券、重复核销等。收银员不可修改余额，制作员不可查询会员余额，店长可修改商品价格。

开发验证曾发现：LineNo是SQL Server关键字，已改为LineNumber；过滤索引要求显式会话选项，已补齐；店长执行带WHERE/表达式的价格更新还需要商品SELECT权限，已补充，并增加更新结果断言。没有将失败轮次写成通过证据。

## 5. 权限实现范围

| 角色 | 阶段一实际授权 |
| --- | --- |
| 收银员 | 读取菜单与订单摘要视图 |
| 制作员 | 只读制作队列视图，不含会员资金和地址 |
| 库存管理员 | 读取原料、库存流水及可用库存视图 |
| 店长 | 读取经营视图，维护商品与券活动 |

跨表资金、库存、订单写入演示由课程数据库管理连接执行，未向普通角色开放直接修改。后续应通过受控业务入口授权，而不是直接授予全库写入。当前角色脚本是第一阶段权限实验，不是完整应用登录系统。员工Job属性、会员身份和实际数据库用户尚未自动关联；骑手与会员逐人数据隔离未实现，不能给他们直接开放基表SELECT。

## 6. 完整性能力与限制

| 规则 | 当前保证方式 |
| --- | --- |
| 主码唯一、候选码唯一、引用存在、字段域合法 | PK、UK、FK、CHECK，由数据库强制 |
| 券归属及同券不能同时占用多个有效订单 | 联合FK与过滤唯一索引 |
| 一单一笔成功支付/全额退款 | 过滤唯一索引 |
| 金额=单价×数量，应付=商品额−优惠+配送 | 计算列；订单头与明细合计另行对账 |
| 优惠券有效期、门槛、可用状态 | 服务演示检查，未封装为通用数据库入口 |
| 余额支付与余额流水、耗料与库存流水一致 | 演示事务及对账断言，不防任意管理员绕过脚本 |
| 原支付与退款同单同渠道同金额、骑手职务、配送与订单状态一致 | 演示流程遵循；跨行通用约束待后续业务入口完善 |
| 预留按订单释放、支付超时、并发重复通知 | 业务需求已定义；当前没有持久化的逐单原料预留表和通用超时处理器 |
| 充值失败及外部结果待核对 | 当前仅演示成功充值流水，尚无独立充值请求/回调表 |
| 已发券规则不可变与配送异常历史 | 业务约定；本版尚无通用审计历史和规则版本机制 |

阶段一实现了课程要求的关系数据库闭环及扩展服务演示，并不宣称已满足生产级外卖与储值系统要求。后续阶段应优先补齐逐单预留、充值请求、身份隔离及事务入口，再扩展界面；库存批次及真实接口继续按范围讨论。

## 7. 实验总结与答辩准备

关系设计要从经营含义出发：充值不是销售收入，订单总额不能在连接明细后重复相加，原料耗用不会因已制作订单退款而自动恢复。数据库约束适合表达单行和引用规则，多表业务一致性还需要受控事务和验证。组员需自己复现脚本，解释字段、键、每项约束的失败原因和权限边界；个人学习体会由本人补充，不以AI代写内容冒充实际经历。
